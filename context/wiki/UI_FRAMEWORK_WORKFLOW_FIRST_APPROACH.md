# Логика UI-фреймворка: первый подход

> Статус: рабочая архитектурная гипотеза  
> Область: Arena/WASM и браузерный DOM

## Назначение

Этот документ фиксирует первое разделение ответственности между ареной и JavaScript. Оно выведено из уже проверенных экспериментов со сменой шаблонов, прямым чтением WASM-памяти и точечным обновлением dirty-узлов.

Это не попытка воспроизвести React или другой существующий фреймворк. Дальнейшая работа со свёрткой графов и комбинаторами может уточнить интерфейсы, но не должна смешивать состояние приложения с его отображением.

## Общий цикл

Любое действие начинается в браузере и проходит один общий путь:

```text
DOM-событие
    ↓
JS Controller
    ↓
команда WASM
    ↓
Arena изменяет состояние
    ↓
JS синхронизирует представление
    ├── изменился active root → Router → Renderer → Bindings
    └── root не изменился     → Dirty Patcher → конкретные DOM-элементы
```

Краткий протокол обработчика:

```text
прочитать параметры события
→ преобразовать их в типы WASM
→ вызвать команду арены
→ выполнить syncView()
```

WASM является автором состояния. JS не изменяет узлы арены прямой записью в линейную память.

## Два класса изменений

### Навигация

Навигация является структурным изменением:

```text
DOM event
→ JS вызывает команду WASM
→ Arena меняет active_page_root
→ JS читает новый подграф
→ Router определяет тип страницы
→ Renderer заменяет шаблон
→ Bindings регистрирует связи новой страницы
```

Арена не знает об HTML и не выбирает DOM-шаблон. Она хранит активный корень и данные подграфа. Маркер страницы внутри подграфа сообщает JS, какой шаблон необходимо показать.

### Изменение внутри страницы

Локальная мутация не меняет активный корень:

```text
DOM event
→ JS вызывает команду WASM
→ Arena изменяет атомы
→ Arena добавляет nodeId в dirty list
→ JS читает dirty list
→ Dirty Patcher обновляет связанные DOM-элементы
```

Повторный обход страницы и замена шаблона для такой мутации не нужны.

Основное правило:

```text
смена корня    → замена шаблона
изменение узла → точечный DOM patch
```

## Границы ответственности

### Arena/WASM

Arena отвечает за:

- граф и object pool;
- состояние приложения;
- активный корень страницы;
- команды приложения и допустимые переходы состояния;
- изменение атомов;
- регистрацию dirty-узлов;
- экспорт чтения состояния для JS.

Arena не знает о DOM, HTML-элементах и способе визуального представления данных.

### JS Controller

Controller:

- принимает DOM-событие;
- извлекает его параметры, например `TopologyID`;
- преобразует строковые DOM-значения в числовые аргументы WASM;
- вызывает команду арены;
- запускает общую синхронизацию представления.

Controller не реализует правила изменения состояния приложения.

### Router

Router:

- сравнивает предыдущий и текущий активные корни;
- при смене корня проходит новый подграф;
- читает маркер типа страницы;
- выбирает соответствующий HTML-шаблон.

Сам обход подграфа не является роутингом. Роутинг начинается в момент интерпретации маркера страницы и выбора шаблона.

### Page Renderer

Renderer:

- клонирует выбранный шаблон;
- материализует начальные значения страницы;
- заменяет содержимое рабочего DOM-контейнера;
- передаёт созданную страницу механизму bindings.

### Bindings

Bindings хранит отображение:

```text
nodeId → DOM-элемент → способ отображения значения
```

Связи создаются при монтировании страницы и удаляются при её замене.

### Dirty Patcher

Dirty Patcher:

- получает список изменённых `nodeId`;
- находит зарегистрированные DOM-элементы;
- читает актуальные значения из арены;
- точечно обновляет DOM;
- после успешного обновления очищает dirty list.

## Страница и элемент

Страница и узел имеют разные масштабы ответственности:

```text
страница → структура и жизненный цикл
узел     → данные и локальное обновление
```

Навигация строит представление сверху вниз:

```text
active root → page marker → template → bindings
```

Локальное обновление идёт непосредственно к конечному элементу:

```text
dirty nodeId → binding → DOM-элемент
```

Минимальный логический UI-модуль на этом этапе — не универсальный компонент, а связь узла с DOM-элементом и способом его отображения. Понятие компонента следует вводить только тогда, когда появятся повторяемые составные блоки с собственным жизненным циклом.

## Предполагаемое функциональное разбиение

В JS выделяются следующие части:

- `ArenaClient` — вызовы WASM и чтение линейной памяти;
- `AppController` — обработка действий и общий workflow;
- `Router` — обработка смены активного корня;
- `PageRenderer` — создание и замена страницы;
- `Bindings` — реестр связей узлов с DOM;
- `DirtyPatcher` — локальные обновления.

В C/WASM разделяются:

- хранение узлов и object pool;
- построение и обход графа;
- состояние навигации;
- команды приложения;
- dirty tracking;
- экспортируемый API.

Это логические границы. Физическое разнесение по файлам выполняется после фиксации минимальных интерфейсов между частями.

## Связь с комбинаторной логикой

Текущий UI-процесс пока использует граф как описание состояния и страниц. Следующий исследовательский слой — выполнение преобразований самого графа:

- свёртка подграфов;
- применение комбинаторов;
- представление пользовательского события как терма или команды;
- получение нового наблюдаемого состояния посредством редукции.

Граница остаётся прежней: Arena вычисляет новое состояние графа, JS материализует наблюдаемую часть этого состояния в DOM. Конкретное место комбинаторов в workflow должно быть доказано отдельным экспериментом.
