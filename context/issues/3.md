# Experiment 3: событие, комбинаторная редукция и растущая WASM-память

## Контекст

Первый Zero-VDOM POC уже подтверждает наблюдаемую цепочку:

```text
C/WASM arena mutation
→ dirty node ID
→ адресное обновление DOM
```

Текущий `increment_node_42()` намеренно сливает получение события, вычисление нового значения и commit. Следующий эксперимент должен разделить эти понятия и исследовать, как внешний факт становится объектом комбинаторного универсума.

Тикет #2 временно приостанавливается, но не закрывается: native x86-64 линия `App` остаётся самостоятельным исследовательским backend.

## Главный вопрос

Что такое событие с точки зрения комбинаторной логики в нашей материальной модели?

В чистой комбинаторной логике нет времени, браузера, изменяемого состояния или событий. Поэтому рабочая гипотеза такова:

> Событие — конечный объект комбинаторного универсума, материализованный внешней средой и добавленный как новый корень вычисления.

Например:

```text
Click(42) = App(CLICK, TARGET_42)
```

`CLICK` является конструктором данных, а не обязанным редуцироваться комбинатором. Внешняя среда отвечает за факт и порядок внесения событий; логика работает уже с их кодировкой.

## Предполагаемая вычислительная граница

```text
external event
→ INJECT: materialize event term
→ REDUCE: HANDLE event state
→ Result(new_state, Dirty(node_id))
→ COMMIT: materialize result in persistent arena roots
→ JS applies the indicated projection
```

Минимальный пример:

```text
event = Click(42)
state = Count(100)

HANDLE event state
    → Result(Count(101), Dirty(42))
```

После отдельного commit:

```text
arena[42] = Count(101)
dirty_nodes = [42]
```

Эксперимент должен проверить, можно ли сохранить вычислительную часть чистой, оставив физическую мутацию границей машины.

## Линейная память WASM

Физически WebAssembly предоставляет одну линейную память. Логически мы исследуем её разделение как минимум на две области.

### 1. Арена графа

Фиксированные по размеру узлы:

```c
struct Node {
    uint32_t tag;
    uint32_t left;
    uint32_t right;
    uint32_t payload;
};
```

Узел содержит:

- тег;
- индексы рёбер аппликации;
- малый примитив непосредственно в `payload` либо handle внешнего объекта.

Внутренние ссылки являются индексами/смещениями, а не физическими адресами.

### 2. Пул динамических объектов

Объекты переменного размера не помещаются внутрь 16-байтового узла. Первый кандидат — строки.

Рабочее представление строки:

```text
StringRef { offset, byte_length }
```

Байты находятся в отдельной логической области той же WASM linear memory. Узел графа несёт только стабильный handle или offset.

На первом этапе исследуем простейший bump allocator:

- последовательное выделение;
- без освобождения;
- без GC;
- без интернирования, пока оно не станет отдельной проверяемой гипотезой.

Кроме строк потенциальными внешними объектами могут стать byte arrays, большие числа и host-resource handles, но они не входят в первый опыт.

## Расширение памяти

WASM-память растёт страницами по 64 KiB через `memory.grow`.

Нужно экспериментально проверить:

1. Как определяется нехватка места в пуле.
2. Кто вызывает рост: C/WASM или host.
3. Сохраняются ли внутренние offsets после роста.
4. Как JS повторно получает view после замены/изменения `memory.buffer`.
5. Какие ссылки запрещено хранить в JS между вызовами.
6. Как сообщается отказ `memory.grow`.
7. Не ломается ли графовая арена при расширении payload pool.

Ключевой контракт: стабильными наружу являются числовые `node_id` и offsets, но не JS TypedArray views и не сырые адреса.

## Порядок минимальных опытов

### A. Зафиксировать текущий baseline

- воспроизводимая сборка `arena.wasm`;
- проверка `payload=100 → 101`;
- проверка `dirty_nodes=[42]`;
- адресное обновление DOM.

### B. Проверить строковый пул

- записать одну UTF-8 строку bump allocator'ом;
- вернуть `offset + length`;
- прочитать её из JS;
- подтвердить неизменность графовых индексов.

### C. Проверить `memory.grow`

- заполнить исходную область пула;
- запросить дополнительную страницу;
- заново создать JS view;
- прочитать строки, записанные до и после роста;
- подтвердить корректность узлов арены.

### D. Материализовать событие как терм

- создать атомы `CLICK` и `TARGET_42`;
- построить `App(CLICK, TARGET_42)`;
- передать индекс терма вычислителю;
- не изменять счётчик на стадии INJECT.

### E. Отделить REDUCE от COMMIT

- `HANDLE event state` получает новый объект результата;
- до commit устойчивый state не меняется;
- commit заменяет наблюдаемый корень или его содержимое;
- dirty ID появляется только вследствие commit.

## Открытые вопросы

- Является ли `COMMIT` частью исчисления или операцией материальной машины?
- Нужны ли специальные примитивные комбинаторы для чисел, строк и событий?
- Представлять результат парой `Result(state, effects)` или отдельными корнями?
- Является ли событие эфемерным корнем и когда освобождается его граф?
- Как различать два одинаковых терма `Click(42)`, поступивших последовательно?
- Должны ли строки быть неизменяемыми и интернированными?
- Делить ли node arena и object pool статической границей или растить их навстречу друг другу?
- Что считать исчерпанием памяти и как оно наблюдается в семантике машины?

## Критерий успеха тикета

Тикет завершён, когда один браузерный click:

1. материализуется в арене как терм события;
2. участвует в наблюдаемой комбинаторной редукции;
3. производит новый объект состояния и dirty ID;
4. отдельно commit'ится в устойчивый корень;
5. обновляет ровно одну DOM-проекцию;
6. не требует хранения авторитетного состояния в JavaScript;
7. остаётся корректным после хотя бы одного успешного `memory.grow`;
8. использует строку из внешнего payload pool, прочитанную после роста памяти.

## Вне рамок

Пока не вводятся GC, free-list, многопоточность, React, Virtual DOM, KV-store, полноценный набор комбинаторов или оптимизация производительности.

Итог эксперимента со строковым пулом (3 октября 2026).

Неутешительная часть: по памяти мы заметно походили по кругу. Смешали сразу несколько разных величин — индекс узла, размер арены в узлах, размер арены в байтах, смещение пула относительно структуры `Memory` и фактическое смещение внутри линейной памяти конкретного экземпляра WASM. Из-за этого некоторое время рассуждали об «адресах», хотя на границе WASM/JS у нас везде целочисленные смещения.

Что в итоге проверено на практике:

- арена узлов и объектный пул объединены в одну структуру `Memory`;
- `get_memory_base()` возвращает фактическое начало этой структуры в линейной памяти WASM;
- начало пула вычисляется как `memory_base + 1_600_000` (`100000 * sizeof(Node)`, где `sizeof(Node) == 16`);
- строковый API возвращает смещение данных относительно пула и длину;
- JS складывает базу структуры, относительное положение пула и смещение строки, после чего читает байты прямо из `WebAssembly.Memory`;
- round-trip подтверждён: после изменения узла получено фактическое смещение `1605128`, длина `3`, строка `bye`;
- браузер обновляет одновременно числовой узел #42 и строковый узел #1 через dirty-список `[42, 1]`;
- `make check` приведён в соответствие новому поведению и проходит.

Вывод: этот участок эксперимента можно считать закрытым. Главное достигнуто — мы умеем получить реальное смещение данных в линейной памяти WASM и прочитать объект на стороне JS. Дальше не стоит снова уходить в обсуждение «машинных адресов»: память остаётся технической подложкой, а следующую работу надо вести уже в терминах логической модели, типов узлов, аппликации, событий и редукции.

Ограничение текущего прототипа зафиксировано сознательно: относительное начало пула `1_600_000` пока захардкожено в JS. Для данного закрытого эксперимента этого достаточно; превращать это сейчас в полноценный allocator или стабильный ABI не требуется.
