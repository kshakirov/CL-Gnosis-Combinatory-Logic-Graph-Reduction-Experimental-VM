# Curry Assembly: минимальная материализация `APP(X, X)` в арене

## Контекст

В исходной алгебре Карри имеются атомарные `obs` и единственный бинарный конструктор аппликации:

\[
X,Y\in Ob \Longrightarrow (XY)\in Ob.
\]

Составной `ob` не является новым атомом. В выражении

\[
(XX)
\]

существуют один атом `X`, два его вхождения и один новый составной объект `App(X, X)`.

Цель Curry Assembly — получить машинное представление, из которого бумажная конструкция восстанавливается без потери различий. Физический путь выполнения и число инструкций не обязаны совпадать с бумажной операцией; должен совпадать наблюдаемый результат.

## Цель тикета

Построить минимальный сквозной эксперимент, в котором отдельная ассемблерная функция для x86-64 материализует в арене один объект:

\[
\operatorname{App}(X,X).
\]

После возврата из ассемблера оболочка на C должна проверить, что машинное состояние однозначно декодируется как `(XX)`.

Эксперимент пока не исследует производительность. Его единственная задача — зафиксировать корректную границу между бумажной операцией `App` и её первым машинным представлением.

## Целевая среда

- Ubuntu Linux;
- x86-64;
- GCC 15;
- GNU assembler через GCC;
- отдельный ассемблерный файл `.S`;
- C используется только как оболочка эксперимента.

Конкретную модель процессора и версию компилятора необходимо записывать в выводе или отчёте эксперимента, поскольку дальнейшее исследование кэшей будет зависеть от физического CPU.

## Минимальная структура проекта

```text
Makefile
src/main.c
asm/app.S
```

На этой ступени не нужны дополнительные модули, аллокатор общего назначения, parser, graph reducer или библиотека измерений.

## Представление арены

Для первого опыта используется массив фиксированных 16-байтовых узлов:

```text
Node:
    +0   uint32 tag
    +4   uint32 left_or_atom
    +8   uint32 right
    +12  uint32 reserved
```

Минимально достаточно двух тегов:

```text
ATOM
APP
```

До вызова ассемблерной функции:

```text
arena[0] = Atom(X)
```

После вызова:

```text
arena[0] = Atom(X)
arena[1] = App(left = 0, right = 0)
```

Индекс `0` обозначает один атомарный `ob`. Два поля со значением `0` обозначают два вхождения этого атома в составной объект, а не создание двух новых атомов.

Реальный payload атома в этом эксперименте не нужен. Достаточно его устойчивой различимости посредством идентификатора.

## Граница C и Assembly

### Оболочка на C

C-код выполняет только следующие действия:

1. Создаёт и обнуляет небольшую арену с корректным выравниванием.
2. Помещает `Atom(X)` в `arena[0]`.
3. Вызывает ассемблерную функцию для создания `arena[1]`.
4. Проверяет поля результата.
5. Сообщает об успехе или ошибке.

C-код не должен самостоятельно выполнять исследуемую операцию `APP`.

### Ассемблерная функция

Ассемблер получает:

- базовый адрес арены;
- индекс или адрес целевого узла;
- индекс левого `ob`;
- индекс правого `ob`.

Она выполняет только три содержательные записи:

```text
destination.tag   = APP
destination.left  = left_index
destination.right = right_index
```

Для первого вызова:

```text
destination = 1
left_index  = 0
right_index = 0
```

Вопрос об интерфейсе через индексы или заранее вычисленный адрес назначения разрешается минимальностью полученного машинного кода и ясностью ABI. Решение необходимо зафиксировать после просмотра дизассемблированного результата.

## Проверяемое соответствие

Пусть `E` кодирует бумажный объект в арену, а `D` читает каноническое наблюдаемое состояние обратно.

Эксперимент должен подтвердить:

\[
D(E(X))=X,
\]

и

\[
D\bigl(\operatorname{APP}_{asm}(E(X),E(X))\bigr)=(XX).
\]

В практической проверке C-оболочка должна установить:

```text
arena[1].tag   == APP
arena[1].left  == 0
arena[1].right == 0
```

При этом `arena[0]` должна остаться неизменной.

## Контроль фактического машинного кода

После сборки необходимо проверить скомпонованный исполняемый файл:

```bash
objdump -d <executable>
```

Проверяется именно фактическая реализация ассемблерной функции, а не только исходный `.S`-файл:

- присутствуют ожидаемые записи полей;
- отсутствуют неожиданные обращения к памяти;
- C не подменил операцию собственной реализацией;
- соглашение о вызовах соблюдено;
- функция возвращается штатно.

Отдельный `.S`-файл выбран для явной границы эксперимента. Причина не в том, что GCC переписывает инструкции inline assembly, а в том, что компилятор может преобразовывать окружающий C-код при неверно описанных ограничениях и эффектах. Внешняя функция делает исследуемый участок проще для проверки.

## Критерии завершения

- [ ] Проект собирается GCC 15 на Ubuntu x86-64.
- [ ] `arena[0]` содержит один различимый атом `X`.
- [ ] Операция создания `arena[1]` полностью реализована в `asm/app.S`.
- [ ] После вызова `arena[1]` содержит `App(0, 0)`.
- [ ] Исходный атом в `arena[0]` не изменяется.
- [ ] C-оболочка завершается с успехом только при точном совпадении всех проверяемых полей.
- [ ] Фактический машинный код проверен через `objdump`.
- [ ] В кратком отчёте зафиксированы CPU, версия GCC, команда сборки и наблюдаемый результат.

## Вне рамок тикета

На этой ступени сознательно не реализуются:

- редукция;
- комбинаторы `B`, `C`, `K`, `S`, `W`;
- обход дерева или графа;
- pointer reversal;
- числа Черча;
- переменные и lambda-компиляция;
- хранение payload атомов переменной длины;
- освобождение или повторное использование узлов;
- сравнение указателей и индексов;
- случайное размещение узлов;
- многопоточность;
- измерения через `perf`;
- исследование L1/L2/L3, TLB и оперативной памяти.

## Следующий эксперимент

После завершения этого тикета можно будет построить один и тот же левый `ob`

\[
T_0=X,
\qquad
T_{n+1}=(T_nX)
\]

в двух физически различных аренах: с последовательным и перемешанным размещением узлов. Тогда `perf` позволит сравнить материальную стоимость обхода при одинаковом декодируемом состоянии. Этот следующий этап не должен расширять текущий минимальный эксперимент.
